# Database Architecture & Implementation Guide

## Blood Bank Donation and Issue Management System
**Target Database:** MySQL 8.0+ / InnoDB Engine  
**Project Role:** College B.Tech DBMS Project Demonstration  

---

## 1. System Overview

The **Blood Bank Donation and Issue Management System** is a mission-critical healthcare information management prototype designed to coordinate blood donor registries, voluntary donation intakes, live component inventory reserves, hospital requisitions, and atomic dispatching.

The database architecture is engineered with the following principles:
- **Relational Integrity:** Foreign key constraints with `ON UPDATE CASCADE` and `ON DELETE RESTRICT` prevent orphaned records.
- **Transactional Consistency:** MySQL ACID transactions ensure that inventory decrement and issue fulfillment occur atomically.
- **Race Condition Prevention:** Explicit row-level locking (`SELECT ... FOR UPDATE`) prevents concurrent double-allocation of rare blood units.
- **Security:** Password hashes created with Werkzeug's `scrypt` algorithm; parameterization prevents SQL injection on all application routes.

## 3. Concurrency Control & Row Locking (`FOR UPDATE`)

In high-concurrency environments (e.g. multiple hospital reception desks accessing inventory simultaneously), two operators might attempt to issue the last remaining unit of **O- negative** blood at the exact same second.

Without row-level locking, a race condition occurs:
1. Operator A checks inventory: 1 unit available.
2. Operator B checks inventory: 1 unit available.
3. Operator A issues 1 unit -> inventory becomes 0.
4. Operator B issues 1 unit -> inventory becomes -1 (violating clinical safety).

### How Our Implementation Solves This:
When processing an issue in `/issues/process`, the application initiates a MySQL transaction:
```python
conn = db.get_connection()
cursor = conn.cursor(dictionary=True)

# 1. Lock the request record
cursor.execute("SELECT * FROM blood_requests WHERE request_id = %s FOR UPDATE", (request_id,))

# 2. Lock the specific blood group inventory row
cursor.execute("SELECT available_units FROM inventory WHERE blood_group = %s FOR UPDATE", (blood_group,))
inv = cursor.fetchone()

# 3. Validate stock sufficiency
if inv["available_units"] < units_needed:
    conn.rollback() # Abort without making any modifications!
    return error

# 4. Atomically deduct stock, record issue, and mark request fulfilled
cursor.execute("UPDATE inventory SET available_units = available_units - %s WHERE blood_group = %s", ...)
cursor.execute("INSERT INTO blood_issues ...", ...)
cursor.execute("UPDATE blood_requests SET status = 'Fulfilled' ...", ...)

# 5. Commit atomically
conn.commit()
```

The `FOR UPDATE` clause places an exclusive lock on the inventory row in the InnoDB buffer pool. Any competing transaction is queued until the first transaction commits or rolls back, completely eliminating race conditions.

## 4. Integrity Constraints Summary

- **Primary Keys:** Every entity has a surrogate auto-increment key or canonical natural key (`blood_group`).
- **Foreign Keys:** Ensure referential integrity between child and parent tables (`ON UPDATE CASCADE ON DELETE RESTRICT`). Deleting a donor with past donation records is strictly blocked by the database engine.
- **Check Constraints (`CHECK`):**
  - `donors.age`: Enforces medical donor age between 18 and 65 years.
  - `inventory.available_units`: Enforces non-negative values (`>= 0`).
  - `donations.units_donated`, `blood_requests.units_required`, `blood_issues.units_issued`: Enforces positive quantities (`> 0`).
- **Unique Constraints (`UNIQUE`):**
  - `users.username`, `users.email`
  - `blood_issues.request_id` (guarantees that a blood request is fulfilled at most once).
